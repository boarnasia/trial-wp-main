# serve のデタッチは serve 自身がデーモンになって行う

`serve up --detach` で開発セッションを端末から切り離すとき、ホストで動くダッシュボードなどのプロセスを誰が面倒を見るかを決める必要があった。serve 自身が監督プロセスを端末から切り離し、PID を `.local/serve.pid`、ログを `.local/logs/` に書き、`serve down` と `serve logs` はそれを手がかりにする方式を採った。あわせて、開発セッションの終了（`down` と Ctrl-C）では共有インフラも止め、セッションの外では何も動いていない状態を正常とした。

## Considered Options

- **ダッシュボードをコンテナに戻し、`docker compose up -d` / `logs -f` に任せる**: デタッチとログ収集をそのまま Docker に任せられるが、コンテナから docker を操作できないためにダッシュボードをホストへ移した判断（host-side-dashboard）を覆すことになるため不採用。
- **launchd や supervisord などの外部のプロセス管理に任せる**: 再起動や常駐の仕組みは堅牢だが、macOS への依存か追加の依存を持ち込み、セッション単位で起動・停止したい用途には重い。
- **終了時に共有インフラを残す（従来の動き）**: 次の起動は MySQL を待たずに速いが、「セッションの外では何も動いていない」という単純な状態の定義を優先した。

## Consequences

- PID ファイルとログファイルの管理（古い PID の扱い、ログの世代）を wp-main が自前で持つ。
- 監督プロセスが異常終了すると、サイトや共有インフラが残ることがある。`serve down` はセッションがなくても残ったものを止めるので、後片付けに使う。
- 毎回のセッション開始で MySQL の起動を待つぶん、`up` は従来より遅くなる。
