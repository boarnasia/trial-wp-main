## Context

`serve` は今、1 つの Python プロセスが次の順に動く（`cli/management/commands/serve.py`）。
1. `session.begin` で共有インフラとサイトを起動する。
2. `processes.supervise` でホストのプロセス（ダッシュボード）を前面で監督する。
3. `finally` で `session.end` がサイトを止める。

ホストのプロセスの出力は、`supervise` の中で端末に流すだけで、どこにも残らない。開発セッションが動いているかどうかは、`health.py` と `devenv uninstall` がダッシュボードのポートの応答で推測している。共有インフラは `power.start_infra`（`docker compose up -d --wait caddy mysql`）で起動するが、止める手段はない。サイトの操作は `power.site_lock`（`.local/locks/` の flock）で直列化している。

動機は proposal.md の Why を、デタッチを serve 自身で行う理由は `docs/adr/0002-serve-daemonizes-itself.md` を参照。

## Goals / Non-Goals

**Goals:**
- 前面とデタッチで、開発セッションを監督するコードを 1 つにする。違いは端末への出力の有無だけにする。
- 開発セッションが動いているかどうかを、PID の再利用やポートの横取りに惑わされずに判定できるようにする。
- `serve down` を、どの状態から実行しても安全な後片付けにする。

**Non-Goals:**
- ホストのプロセスの自動再起動（落ちたらセッションを終える）。
- 開発セッションを複数同時に動かすこと。
- ログの 1 世代を超える保存や、サイズによるローテーション。
- vite などのホストのプロセスを追加すること（一覧に足せる形は保つ）。

## Decisions

### D1. デタッチは自分自身を別セッションで起動し直す（fork しない）
`serve up --detach` は、同じコマンドを隠しサブコマンドで起動し直す。起動には `subprocess.Popen(start_new_session=True)` を使い、stdin・stdout・stderr は `/dev/null` とログにつなぐ。起動し直した子が開発セッションの監督プロセスになり、前面の `serve up` と同じ関数を端末への出力なしで実行する。
- **代替: `os.fork()` による二重 fork:** macOS では、スレッドや Objective-C のランタイムを初期化した後の fork が不安定で、Django の読み込みでそれが起こる。起動し直す方式なら、子はきれいな状態から始まる。
- **代替: python-daemon などのライブラリ:** 起動し直す方式なら、依存を増やさずに済む。

### D2. 開発セッションの判定は、PID ファイルの flock で行う
監督プロセスは、`.local/serve.pid` を開いて排他の flock を取る。flock はセッションが終わるまで持ち続け、PID と状態（`starting` / `ready`）を JSON で書く。ほかのコマンドは、同じファイルに非ブロッキングの flock を試して、開発セッションが動いているかを判定する。
- flock が取れなければ、セッションは動いている。この場合、ファイルの PID を信じてよい。
- flock が取れれば、セッションは動いていない。このとき残っているファイルは古いものなので、`down` や `up` が削除する。

`check-health` は、flock を取ってすぐ放すだけで、ファイルを書き換えない。
- **代替: PID の生存確認（`os.kill(pid, 0)`）:** PID の再利用で誤判定する。flock なら、プロセスが死ねば OS が必ず解放する。
- **代替: ダッシュボードのポートの応答（今の方式）:** 起動中や、ダッシュボードだけが落ちた瞬間を判定できない。別のプロセスがポートを使っていても誤判定する。

### D3. `--detach` の完了待ちは、状態と子の生存で判断する
親（`serve up --detach` を実行したプロセス）は、次の 2 つを監視する。
- **PID ファイルの状態が `ready` になる:** URL を表示して exit 0 で終わる。
- **子が終了する:** 子の終了コードと、`.local/logs/serve.log` の末尾を表示して exit 1 で終わる。

子は、ホストのプロセスを起動した後、ダッシュボードのポートの応答を最大 120 秒待ってから `ready` を書く。応答しなければ、セッションを終えて exit 1 で終わる。共有インフラとサイトの起動にかかる時間は、既存のタイムアウト（各 120 秒）に任せ、親の側では全体のタイムアウトを持たない。

### D4. 開発セッションの終了は、シグナルで監督プロセスに頼む
- **`serve down` が SIGTERM を送る:** セッションが動いていれば、PID に SIGTERM を送り、flock が解放されるまで待つ（上限 300 秒）。監督プロセスは、次の順で片付けて exit する。
  1. ホストのプロセスを止める。
  2. 動いているサイトを `session.operate` で止める。履歴には出どころ `serve` で記録する。
  3. 共有インフラを止める。
- **後片付け:** `down` は続けて、セッションの有無にかかわらず、残っているサイトを止めて共有インフラを止め、古い PID ファイルを消す。何度実行しても結果は同じになる。
- **`serve up` による入れ替えは SIGUSR1 を送る:** 監督プロセスは、ホストのプロセスとサイトだけを止めて exit する。共有インフラは止めない。新しい `up` は flock を取ってから、自分のセッションを始める。
- **前面の Ctrl-C（SIGINT）:** SIGTERM と同じ扱い。

ホストのプロセスは、今と同じく `start_new_session=True` で起動し、監督プロセスが順に止める。

### D5. 共有インフラの停止は `docker compose down`（`-v` なし）
`power.stop_infra` は、wp-main の Compose プロジェクトで `docker compose down --remove-orphans` を実行する。サイトは先に `operate` で止めて履歴を残してから、プロジェクトごと片付ける。削除されるものと残るものは次のとおり。
- **削除される:** コンテナと内部ネットワーク `wp-db`。
- **残る:** 名前付きボリュームと、外部ネットワーク `wp-global-net`。

次の `up` で、コンテナとネットワークは作り直される。
- **代替: `docker compose stop caddy mysql`:** 停止したコンテナが残り続け、`docker ps -a` が散らかる。用語の「開発セッションの外では何も動いていない」とも、`down` の名前ともずれる。

### D6. ログはホストのプロセスごとのファイルに書き、`logs` は束ねて表示する
- **出力の書き先:** `supervise` の出力の中継（pump）は、各行を `.local/logs/<名前>.log` に追記し、前面のときだけ端末にも流す。監督プロセス自身の出力（「wp1 を起動します」やエラー）は `serve.log` に書く。セッション開始時に、既存の `*.log` を `*.log.1` に置き換える。
- **`serve logs` のログの読み方:**
  - ホストのプロセスのログ（`serve` と `dashboard`）は、ファイルを読む。`-f` では追記を追う。
  - コンテナのログは、`docker compose logs --no-log-prefix [-f] [--tail N] <service>` をサービスごとに起動して読む。
- **`serve logs` の出力:** 各ストリームの行を、スレッドから `名前 | 行` の形で 1 本の標準出力に流す。
- **名前:**
  - `serve`、`dashboard`（ホストのプロセスの一覧の名前）
  - `caddy`、`mysql`
  - サイト ID（`wp1` は `wp1-wordpress` に対応する）
- **名前を省いたとき:** ホストのプロセスのうちログファイルのあるものと、起動している共有インフラとサイトを出す。

### D7. 「自分で起動した共有インフラを止める」は、呼び出し側が判定する
`install` と migration 6 は、共有インフラを起動する前に開発セッションが動いているかを D2 の方法で確かめ、動いていなければ最後に `power.stop_infra` を呼ぶ。止めるのは `try/finally` の中なので、失敗しても共有インフラは残らない。`rebuild_if_running` は、プロキシが起動しているときだけ作り直す。この関数は共有インフラを新しく起動しないので、変更しない。

### D8. `check-health` の共有インフラの項目は、セッションの判定を前提にする
- **セッションの判定:** 新しい内部項目を加え、開発セッションの内外を判定する。
- **セッションの外で SKIP にする項目:**
  - 共有インフラのコンテナの項目
  - ダッシュボードのプロセスの項目

  SKIP の理由は「開発セッションの外です（`uv run manage.py serve up` で始まります）」とする。
- **連鎖して SKIP になる項目:** サイト、HTTP、CA は、今の前提関係に従って連鎖する。
- **ダッシュボードのプロセスの項目:** セッション中に応答しないときは FAIL にする。
- **表示:** 判定の項目自体は、出力の一覧に出さない。

## Risks / Trade-offs

- [監督プロセスが SIGKILL などで死ぬと、サイトと共有インフラが残る] → flock は解放されるので、次の `up` と `down` は古いセッションとして扱い、残ったものを片付ける。
- [`down` の待ち時間の上限（300 秒）を超えても監督プロセスが止まらない] → SIGKILL を送ってから D4 の後片付けを続ける。どちらになったかを表示する。
- [毎回のセッションで MySQL の起動を待つので、`up` が遅くなる] → ADR 0002 で受け入れた。入れ替えのときは共有インフラを止めない。
- [`docker compose down` がサイトのコンテナも削除する] → サイトのデータは共有 MySQL のボリュームと各サイトの `wpN-html` ボリュームにあり、コンテナの削除では失われない。
- [デタッチ中の `serve.log` に、サイトの起動の失敗しか残らない] → `up --detach` が終わるときに、失敗したサイトを端末にも表示する。子の `serve.log` の該当行を読んで表示する。
- [ダッシュボードから止めたサイトのログが、`serve logs` の既定の一覧から消える] → 名前を指定すれば、停止したコンテナの既存のログも出る（`docker compose logs` の動き）。

## Migration Plan

- **環境の移行:** 環境のバージョンを上げる migration は不要。変わるのはコマンドと実行時の動きだけで、Docker のリソースや `.env` は変わらない。
- **既存の環境:** 共有インフラが動いたまま残っていることがある。最初の `serve down`、または次のセッションの終了で止まる。README に `serve down` で片付けられることを書く。
- **サイトのリポジトリ:** 開いている PR（boarnasia/trial-wp-wp1#1・boarnasia/trial-wp-wp2#1）の README の `serve --site` を `serve up --site` に直すコミットを、同じブランチに追加する。
- **ロールバック:** このコミットを戻せばよい。残ったコンテナは `docker compose down` で片付けられる。
